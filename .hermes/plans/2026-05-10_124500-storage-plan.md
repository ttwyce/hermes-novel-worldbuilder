# 追踪文件存储方案分析

## 目标
评估更优的数据存储方案，替代当前纯 MD 文本存储。

---

## 现状分析

### 当前存储方式
4 个 MD 文件，结构各异：

| 文件 | 结构特点 | 读取方式 | 问题 |
|------|---------|---------|------|
| 进度看板.md | 表格 | 整行匹配/替换 | 格式脆弱，多列时易出残留 |
| 剧情线追踪.md | 分级标题 + 正文 | `---` 分割 + 字符串查找 | 插入位置依赖特定分隔符 |
| 编年史.md | 多表格 | 逐行解析 `\|` 表头 | 表格定位复杂 |
| 角色弧光追踪.md | 混合 | 字符串匹配 | 难以做条件查询 |

### 实际使用场景
- **写入**：`post_chapter.py` 每写完一章调用一次，只追加/更新本章数据
- **读取**：人工查看为主，偶尔 grep 搜索
- **写入频率**：150 章 × 1 次/章 = 150 次
- **读取频率**：人工随时查看 + 脚本验证

## 候选方案对比

### 方案 A：保持 MD（现状）

| 优点 | 缺点 |
|------|------|
| 人可读、可直接编辑 | 格式脆弱（见现状分析） |
| 无需转换 | 难以做条件查询 |
| Git 友好（diff 清晰） | 各文件结构不统一，维护成本高 |

### 方案 B：JSON（单文件或分文件）

```json
{
  "chapters": {
    "1": { "title": "...", "words": 3051, "status": "done", "core_event": "..." },
    "12": { "title": "...", "words": 2559, "status": "done", "core_event": "..." }
  },
  "characters": { ... },
  "chronicle": [ ... ]
}
```

| 优点 | 缺点 |
|------|------|
| 结构化，解析简单 | 追加/更新需要全量读写 |
| 可复用（统计、导出） | 人可读但不够直观 |
| 一文件包含所有数据 | 大文件（150章+后） |

### 方案 C：SQLite（推荐）

```sql
CREATE TABLE chapters (
  id INTEGER PRIMARY KEY,
  title TEXT,
  words INTEGER,
  status TEXT DEFAULT 'pending',
  core_event TEXT,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE character_arcs (
  id TEXT PRIMARY KEY,  -- A01, A02...
  name TEXT,
  arc_type TEXT,
  current_stage TEXT,
  updated_chapter INTEGER
);

CREATE TABLE chronicle (
  chapter_id INTEGER,
  time_label TEXT,
  event TEXT,
  chapter INTEGER
);
```

| 优点 | 缺点 |
|------|------|
| 结构化，可 SQL 查询 | 需要数据库文件 |
| 原子性更新（不丢数据） | 需要 Python sqlite3（标准库，无依赖） |
| 单一文件，无冗余 | 人直接读需要工具 |
| 易于扩展（加字段、索引） | |

### 方案 D：YAML

| 优点 | 缺点 |
|------|------|
| 人可读、可直接编辑 | Python yaml 需第三方库（pyyaml） |
| 结构化但比 JSON 直观 | 追加/更新需全量读写 |
| 嵌套结构友好 | 不如 JSON 适合程序解析 |

### 方案 E：CSV（表格数据）

| 优点 | 缺点 |
|------|------|
| 电子表格直接打开 | 不适合嵌套/混合结构 |
| 简单，解析快 | 进度看板/角色弧光追踪用不了 |

---

## 推荐方案

### 选择：方案 C（SQLite）+ 保留 MD 可读层

**核心理念**：程序用 SQLite，保留 MD 用于人工阅读

```
小说根目录/
├── .tracking/
│   ├── tracking.db          # SQLite 数据库（程序用）
│   └── export/
│       ├── 进度看板.md      # 导出生成（人工看）
│       ├── 剧情线追踪.md
│       ├── 编年史.md
│       └── 角色弧光追踪.md
└── 正文/
```

**post_chapter.py 改造**：
1. 写入 SQLite（原子操作）
2. 调用导出函数刷新 MD 文件（供人工阅读）
3. 验证时优先查 SQLite，MD 仅作参考

**优点**：
- 数据结构清晰，查询不依赖字符串解析
- 自动生成 MD（格式永远正确，不会出现残留列问题）
- 数据库单一文件，方便备份
- SQLite 是 Python 标准库（`import sqlite3`），零额外依赖

## 风险与权衡

| 风险 | 应对 |
|------|------|
| SQLite 文件损坏 | 定期 `cp tracking.db tracking.db.bak` |
| MD 文件过时（未及时 export） | post_chapter 每次都 export，或加定时任务 |
| 用户习惯直接改 MD | export 是幂等的，commit 前自动 export |
| 多设备同步 | SQLite 是单文件，Git 支持好（blob 模式） |

## 开放问题

1. **MD 文件是否还保留手写区域？**（如角色弧光追踪的详细分析）→ 可以保留，数据库记录变化点，MD 保留人工补充
2. **迁移时是否保留 git 历史？** → 可以，但 MD 文件重写会导致历史割裂（建议新方案从当前 commit 开始）
3. **是否要给 tracking_db 加读写锁？** → 子代理串行执行，无需锁

## 结论

推荐迁移到 **SQLite + 自动导出 MD** 方案：
- 数据结构化，查询不依赖字符串解析
- MD 文件自动生成，永远格式正确
- 零额外依赖（Python 标准库）
- 单一文件，方便管理
